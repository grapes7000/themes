# How the Starship prompt redesign (and its demo) was built

This documents the process behind the two-line, Powerlevel10k-style Starship
prompt now generated by `theme_starship.py`, and specifically how the preview
artifact was put together before any of it landed in the real config
generator. It's written so a future session (or a future you) can retrace the
same steps without rediscovering the same two bugs the hard way.

## 1. The goal

Replace the single-line Starship prompt with a two-line layout inspired by
Powerlevel10k:

```
 <os> user@host  <dir icon> ~/path   branch +2 ~1 ?1         <lang> v22 <duration> 3s <battery> 84%  2:30 PM
╰─ ❯
```

Left side: OS icon → user@host (only when it matters — SSH or root) →
directory → git → detected languages/tools. Right side (`right_format`):
command duration, failed-status code, background jobs, battery, clock.
Second line: just the arrow.

Everything has to come from the theme's own color-role dict (`r["bg"]`,
`r["accent"]`, etc.) — no theme-specific hex values hardcoded — because the
same generator runs for every theme in `hypr/themes/*.json`.

## 2. Picking real icons instead of guessing

Nerd Font glyphs live in Private Use Areas, so there's no way to eyeball
whether a codepoint I remember (or half-remember) actually exists in the
font the terminal will use. Guessing wrong means a tofu box (☐) in the
prompt instead of an icon. So before writing a single line of TOML, I
built a small verification pipeline:

**Step 1 — dump the installed font's character coverage.** `fontconfig`
can print a font's full Unicode coverage as a bitmap:

```bash
fc-query "/usr/share/fonts/TTF/JetBrainsMonoNerdFontMono-Bold.ttf" \
  | sed -n '/charset:/,/^\t[a-z]* :/p' > /tmp/charset.txt
```

That output looks like:

```
charset:
 0000: 00000000 ffffffff ffffffff 7fffffff ...
 f024: ffffffff 0000001b 00000000 00000000 ...
```

Each line is a run of 256 codepoints (`0xhi00`–`0xhiff`), encoded as eight
32-bit words, one bit per codepoint. A tiny parser turns that into a
`{codepoint: True}` lookup:

```python
import re

bitmap = {}
with open('/tmp/charset.txt') as f:
    for line in f:
        m = re.match(r'^([0-9a-fA-F]+):\s+(.+)$', line.strip())
        if not m:
            continue
        hi = int(m.group(1), 16)          # the high bits of the codepoint
        for word_index, word in enumerate(m.group(2).split()):
            val = int(word, 16)
            base = (hi << 8) + word_index * 32
            for bit in range(32):
                if val & (1 << bit):
                    bitmap[base + bit] = True   # this codepoint IS in the font
```

**Step 2 — get real names for candidate codepoints**, instead of trusting
memory. The Nerd Fonts project publishes a `glyphnames.json` mapping every
icon name (`md-kubernetes`, `dev-python`, `linux-archlinux`, ...) to its
codepoint:

```bash
curl -fsSL https://raw.githubusercontent.com/ryanoasis/nerd-fonts/master/glyphnames.json \
  -o glyphnames.json
```

```python
import json
data = json.load(open('glyphnames.json'))

def find(*substrs):
    """All glyph names containing every substring, with their codepoint
    and whether the installed font actually has it."""
    out = []
    for name, v in data.items():
        if name == "METADATA":
            continue
        if all(s in name for s in substrs):
            cp = int(v["code"], 16)
            out.append((name, cp, cp in bitmap))
    return out

for name, cp, ok in find("md-kubernetes"):
    print(f"{'+' if ok else 'MISSING'} {name} U+{cp:05X}")
# + md-kubernetes U+F10FE
```

This caught real mistakes: my first guess for "conda" was the 🅒 emoji from
the spec, which isn't a Nerd Font glyph at all and isn't in the font —
swapped for `nf-fa-flask` (`U+F0C3`) instead. My guess for Linux Mint's
icon (`linux-linux_mint`) didn't exist under that name; the real one is
`linux-linuxmint` (`U+F30E`). Small thing, but it's the difference between
an icon and a box.

I also used [`fontTools`](https://github.com/fonttools/fonttools) to read
glyph *names* straight out of the font, which is how I confirmed the two
Powerline "rounded cap" characters aren't interchangeable:

```python
from fontTools.ttLib import TTFont
f = TTFont("JetBrainsMonoNerdFontMono-Regular.ttf", lazy=True)
cmap = f.getBestCmap()
for cp in [0xe0b0, 0xe0b4, 0xe0b6]:
    print(hex(cp), cmap.get(cp))
# 0xe0b0 pl-left_hard_divider        <- the flat triangle divider
# 0xe0b4 ple-right_half_circle_thick <- closing rounded cap
# 0xe0b6 ple-left_half_circle_thick  <- opening rounded cap
```

Without those names I'd have been guessing which rounded glyph goes at the
*start* of a segment versus the *end* — and the spec explicitly warned
about "no random triangles with the wrong background color."

## 3. Bug #1 — TOML table ordering

Early version of the generated config looked like this:

```toml
[palettes.theme]
bg = "#0A0A0F"
accent = "#00E5FF"

"$schema" = 'https://starship.rs/config-schema.json'
add_newline = false
format = "..."
```

`starship print-config` rejected it:

```
Failed to load config value: Error in 'StarshipRoot' at 'palettes':
Error in 'StarshipRoot' at 'theme': Error in 'StarshipRoot' at 'add_newline':
invalid type: boolean `false`, expected a string
```

The reason: in TOML, once a `[table]` header appears, every bare `key =
value` line after it belongs to *that table* until another header shows
up. Since `"$schema"`, `add_newline`, and `format` came *after*
`[palettes.theme]`, they were being parsed as `palettes.theme."$schema"`,
`palettes.theme.add_newline`, etc. — and `add_newline`'s boolean `false`
doesn't fit where the palette expects a color string.

**Fix:** emit every root-level key *before* any `[table]` header:

```python
# root keys first — schema, format, right_format, add_newline, palette name
header = '"$schema" = \'...\'\nadd_newline = false\nformat = """..."""\n'

# THEN the palette table
palette = '[palettes.theme]\nbg = "..."\n...'

# THEN every module table
body = '[os]\n...\n[directory]\n...'

out = header + palette + body
```

I only caught this because I validated with `tomllib.load()` (Python's
built-in TOML parser) and `starship print-config` on every iteration,
rather than assuming the string concatenation was correct just because it
"looked right."

## 4. Bug #2 — glyphs vanishing (or worse, mutating) in transit

This was the subtle one. While building the demo, a config that had
validated fine moments earlier suddenly rendered with the opening
Powerline cap and the OS module *completely missing* — not miscolored,
just absent, as if the modules produced empty output.

`starship timings` narrowed it down: the modules *were* running, but a
`[custom.dir_close]` connector that should have printed a single rounded
cap glyph printed nothing. Direct inspection of the file bytes explained
why:

```python
data = open('config.toml', encoding='utf-8').read()
i = data.index('[custom.dir_close]')
snippet = data[data.index('format', i):data.index('format', i) + 40]
print(repr(snippet))
# 'format = "[](fg:accent)"\n\n[git_branch]\ns'
#              ^^ nothing between the brackets — the glyph never arrived
```

The character I'd typed directly into that config — a Nerd Font glyph
above `U+FFFF`, which needs a *surrogate pair* once encoded to UTF-16 —
had silently dropped out somewhere between "the model wrote this
character" and "the character is on disk." A later test showed it can be
worse than dropping: some five-hex-digit glyphs came through as a lone
unrelated ASCII letter instead of vanishing.

I confirmed the pattern by writing every glyph I planned to use into a
file and checking which ones survived:

```python
chars = {
    "folder": "\U000f024b",   # 5 hex digits -> above U+FFFF (astral plane)
    "git_branch": "",        # typed as a literal char in the tool call
    "cap_open": "",          # ditto
}
for name, ch in chars.items():
    print(name, [hex(ord(c)) for c in ch] or "EMPTY")
# folder      ['0xf024b']   <- survived: it was built with \U escapes
# git_branch  EMPTY         <- vanished: it was a literal pasted character
# cap_open    EMPTY         <- same
```

Every glyph that arrived intact had been written as a Python escape
(`"\U000f024b"`) or, better, as a runtime call — never as a literal
character pasted straight into a tool call. Every glyph that got lost or
mangled had been typed as a literal character.

**The fix, applied everywhere from that point on:** never type a Nerd
Font glyph directly into a file. Build it from its integer codepoint at
runtime instead:

```python
# Bad — a literal character in the source, at risk of being dropped or
# mangled by whatever this text passes through before it reaches disk:
symbol = ""

# Good — plain ASCII source, the actual character only exists once Python
# runs chr() on the integer:
symbol = chr(0xf024b)
```

This is exactly why `theme_starship.py` now has a `_G` dict of `chr(...)`
calls at the top instead of glyphs inlined into the TOML template — it's
not a style preference, it's the only version of this file I could
verify was byte-for-byte correct:

```python
_G = {
    "folder": chr(0xf024b),
    "git_branch": chr(0xf418),
    "conflicted": chr(0xf0026),
    # ...
}
```

I then wrote a self-check into the build step so this class of bug can
never silently reappear — after writing the file, confirm every intended
glyph is actually present in it:

```python
written = open(outpath, encoding='utf-8').read()
missing = [name for name, ch in G.items() if ch not in written]
print("missing:", missing or "NONE - all glyphs present")
```

## 5. Escaping, twice over

Two unrelated escaping rules stacked on top of each other and needed to be
handled in the right order:

**Starship's own escaping.** Inside a Starship format string, `(` and `)`
group content conditionally — to show a *literal* parenthesis (like around
a Kubernetes namespace: `context (namespace)`), Starship wants a
backslash-escaped paren: `\(` `\)`.

**TOML's escaping**, on top of that. A single backslash isn't a valid
escape inside a basic TOML string on its own — TOML requires `\\` to
represent one literal backslash. So to get Starship's `\(` into the actual
config file, the TOML source needs `\\(`.

**Python's escaping**, on top of *that*, if the TOML is built inside a
plain (non-raw) Python string — `\\` in a Python string literal already
means "one backslash", so to end up with `\\(` in the written file, the
Python source itself needs `\\\\(` (four backslashes, collapsing to two
after Python parses them, which TOML then collapses to one, which
Starship then treats as an escaped paren):

```python
# Python source:
format = "[$symbol$context( \\\\($namespace\\\\)) ](bold accent2)"
#                            ^^^^ 4 backslashes in source
# -> written to the TOML file as:      \\($namespace\\)
# -> TOML decodes that to:              \($namespace\)
# -> Starship reads that as a literal:  (namespace)
```

Getting this wrong doesn't crash loudly — it either produces a stray
backslash in the prompt or, if the count is off by one, a hard
`tomllib.TOMLDecodeError: Unescaped '\' in a string`. Validating with
`tomllib.loads()` after every change caught this immediately instead of
leaving it as a mystery for whoever hit it in a real terminal.

## 6. Building the actual demo

Once the config validated, I needed *proof* it rendered the way I
intended — not just "the TOML is well-formed," but "here's what actually
prints." Two layers of validation, cheapest first:

```bash
# 1. Structural: does starship accept every field name and value?
STARSHIP_CONFIG=./preview.toml starship print-config   # no warnings = OK

# 2. Behavioral: what does it actually print, in real scenarios?
mkdir demo_plain demo_git && cd demo_git && git init -q
echo "print('hi')" > app.py && git add app.py && git commit -qm init
echo "print('changed')" >> app.py        # -> 1 modified file
echo "new" > untracked.txt               # -> 1 untracked file

STARSHIP_CONFIG=./preview.toml starship prompt                       # plain dir
STARSHIP_CONFIG=./preview.toml starship prompt --status 1             # failed cmd
STARSHIP_CONFIG=./preview.toml starship prompt --right --status 1 \
  --cmd-duration 3000 --jobs 1                                        # right side
```

`starship prompt` prints the real prompt shell-escaped (e.g.
`%{...%}` around each color code for zsh), which is exactly what your
shell would receive. Stripping those wrappers for a plain-text read is a
one-line `sed`:

```bash
sed -E 's/%\{[^}]*%\}//g'
```

This is also how I caught the "duplicate folder icon" bug: the top-level
`format` string wrapped `$directory` in its own icon and styling
(`[ 󰉋 $directory ](...)`, while the `[directory]` module *itself* already
renders its own icon via its own `format` — so the icon printed twice.
The fix was to reference bare `$directory` in the top-level format and
let the `[directory]` module own all of its own presentation, the same
way every other module (`$git_branch`, `$os`, ...) is referenced bare.

I also used `starship timings` (shows each module's raw output plus how
long it took) and `starship explain` (shows each rendered segment next to
a one-line description of what it is) as fast ways to see *which* module
produced *what*, without needing a real terminal.

## 7. The HTML preview artifact

The artifact you were shown is a literal transcription of the validated
`starship prompt` output into HTML `<span>`s with matching
`background`/`color`, using the same y2k theme's actual hex values as CSS
custom properties — not a redrawn mockup:

```css
:root {
  --bg: #0A0A0F;       /* r['bg']      */
  --surface: #15121A;  /* r['bg_alt']  */
  --accent: #00E5FF;   /* r['accent']  */
  --accent2: #FF1493;  /* r['accent2'] */
  --urgent: #FF0055;   /* r['urgent']  */
}
```

Each Powerline segment is one `<span>` with an inline `background`/`color`
pulled from those tokens, laid out with no gaps so the pills read as one
continuous bar, exactly like the real terminal render:

```html
<span style="background:var(--accent);color:var(--bg)">
  &#xf024b; demo_plain
</span>
```

Note `&#xf024b;` — an HTML numeric character reference — instead of the
literal glyph. Same reasoning as Bug #2 above: writing the raw character
into the artifact's HTML source risks it being dropped or mangled before
the file is ever saved. A numeric reference is plain ASCII text; the
*browser* is what turns it into the actual glyph, at render time, so
there's nothing for the transmission path to lose. Before publishing, the
same self-check as before confirmed every reference decodes to the
intended codepoint:

```python
import re
data = open('preview.html', encoding='utf-8').read()
literal_non_ascii = sorted({c for c in data if ord(c) > 127})
refs = sorted(set(re.findall(r'&#x([0-9a-fA-F]+);', data)))
# literal_non_ascii should be empty (or only plain punctuation like em dash);
# refs should list every codepoint you intended to use, in hex
```

## 8. Landing it in the real generator

Once the design was approved against the demo, it was ported into
`theme_starship.py`'s `render()` function rather than inlined into
`gen_starship()` in `theme`, so the existing `starship-config` curses TUI
(which lets you retune icons and thresholds without touching code) keeps
working on top of it. The bundle toggles (`dev_enabled`,
`container_enabled`, `cloud_enabled`, plus the individual
`battery_enabled` / `memory_enabled` / `time_enabled` / `os_enabled`
switches) are new profile keys with the same shape as the existing
`duration_enabled` / `jobs_enabled` pattern, so turning a group off is
just an empty string spliced into the format instead of a conditional
branch:

```python
dev = "$python$nodejs$rust$golang$java$lua$php$ruby$package" if on("dev_enabled") else ""
```

If it's off, that whole stretch of the format string is simply absent —
no empty segment, no stray divider, nothing to clean up.
